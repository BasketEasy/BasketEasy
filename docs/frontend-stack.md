# Kluvo — Frontend Technology Stack

Builds on `architecture.md`'s frontend layer (React SPA, TanStack Query, Context, react-hook-form + zod, i18n FR-default). This fills in the concrete picks.

## Core

| Concern         | Choice                | Why                                                                                   |
| --------------- | --------------------- | ------------------------------------------------------------------------------------- |
| Framework       | React 18 + TypeScript | team familiarity, largest ecosystem                                                   |
| Build tool      | Vite                  | fast dev/HMR, simple SPA setup (no SSR need — internal/club-auth app, not SEO-driven) |
| Package manager | pnpm                  | fast, disk-efficient                                                                  |
| Routing         | react-router-dom v6   | standard, handles nested routes for Club/CTC context + protected routes               |

## Data fetching & server state

TanStack Query owns everything that comes from the API. This section is the guide for writing a hook or a mutation; the `server-state` skill (`.claude/skills/server-state/SKILL.md`) is the checklist to run through on your own diff, and `CLAUDE.md` "Server state" is the one-line version of each rule. It describes what the code does since the caching overhaul (the audit, the seven PRs and their request counts are in the PR descriptions, not here).

| Concern            | Choice                                                                                      | Why                                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Query/cache layer  | TanStack Query                                                                              | caching, background refetch, optimistic updates for RSVP/scoresheet status                                                   |
| Query hook naming  | `use<Model><Method>`, e.g. `useClubCreate`, `useClubList`, `useClubShow`, `usePlayerUpdate` | model-first name is greppable/sortable by domain across the whole hooks folder                                               |
| Query hook files   | one hook per file (not grouped into a shared `useClub.ts` with multiple exports)            | keeps diffs small and each hook independently locatable/importable                                                           |
| HTTP client        | bare `fetch`, wrapped in a singleton `ApiClient` class                                      | no dependency; one place to hold base URL, default headers, auth header injection, 401/refresh handling, error normalization |
| Auth token refresh | handled inside `ApiClient` (queue requests on 401, refresh, retry)                          | keeps refresh logic in one class instead of scattered interceptors                                                           |
| Realtime (later)   | none for v1; revisit WebSocket/SSE if chat/live scoreboard gets built                       | avoid over-building before P1/P2 features ship                                                                               |

### Client setup

- `createQueryClient()` (`app/src/api/queryClient.ts`) is the only place a product `QueryClient` is built (`main.tsx`). Its defaults are `staleTime: FRESHNESS.live` and a retry policy: never on an `ApiError` below 500, at most two retries on a 5xx or a network error. A 4xx is a fact about the request (forbidden, not found, invalid), so repeating it only repeats the refusal; before the policy a 403 cost four requests and did it again on every mount. A hook that sets its own `retry` (`retry: false` on the poule results, whose server scrapes FFBB on every attempt) or `staleTime` keeps it.
- Tests do not copy these defaults. `renderWithProviders` (`app/src/testUtils.tsx`) and `createSeededCache` (`app/src/clubs/testCache.ts`) each build a client with `retry: false` and the library's `staleTime: 0`, so a test that wants a hook's own tier reads it from the hook. A new test uses one of the two; it does not write another `new QueryClient`. 37 older test files still build their own, a migration left for a follow-up.
- Under `React.StrictMode` (`main.tsx`, and the tests that wrap in it), an initial fetch can be sent twice with the first one aborted: the simulated unmount drops the observer and the abort is real since every `queryFn` forwards its signal. It is not a bug, and a test that counts requests under `StrictMode` has to allow for it. The session restore is the one fetch that must not repeat; it is protected by the shared refresh, see below.

### Freshness tiers

Every query hook sets `staleTime` from `FRESHNESS` (`app/src/api/freshness.ts`), never a literal and never the default by omission.

| Tier     | Time    | Use it for                                                                                                                                                                                                                                     |
| -------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `live`   | 30 s    | what several people change at the same time: an event, its RSVP roster, convocations, the wash duty and rotation, the WhatsApp share, the guest page, an unconfirmed scoresheet, invite and guardian status read by an admin who waits         |
| `feed`   | 60 s    | polled or always mounted: the notification feed (its `staleTime` equals its poll interval), the upcoming agenda (`useMyAgenda` default), the back-office stats                                                                                 |
| `slow`   | 10 min  | what others change rarely: rosters and lists, the club list, personas, the team's admins and admin candidates, season stats, poule results, team and club settings that carry derived fields, the past-matches agenda, non-audited admin lists |
| `static` | forever | the session, the push public key, invite previews, `useClubShow`, `useTeamShow`, the team's partner clubs and FFBB links, meeting settings, a confirmed scoresheet, audited back-office reads                                                  |

The rule: **`static` only when the data is immutable or changed solely by mutations that already write the cache.** If another person, a server job or the calendar can change it while someone is looking, it is finite. The plan proposed `static` for several more hooks; each was checked against every writer of its data, not only the logged-in user's mutations, and these became finite with the reason as a comment on their `staleTime`: the admin list and candidates (another manager grants a role, or a player accepting an invite adds a club member), season stats (awards count every teammate's vote and `current` rolls over on 1 September), poule results (FFBB records a result), the child's profile (co-guardians edit it).

- **`gcTime` is the other half.** It stays at the library's 5 minutes: an entry unused that long is discarded, so the next visit refetches. That is what bounds `static` for page-scoped data. A query that is always mounted (the header's club list, the persona list held by `ActingAsProvider`, the bottom nav) is never discarded, so `static` would last until a reload: those take a finite tier, which is why `useClubList` is `slow` while `useClubShow` is `static`.
- **A tier can be a function of the cached data.** `useEventVoteResults(…, startsAt)` is `live` until its window closes, `static` after; `useEventScoresheetStatus` and `useEventScoresheetExtraction` are `static` once `CONFIRMED` (a confirmed sheet is never replaced) and `useMatchStats` is `slow` once it has lines. A time-dependent one compares the **fetch** time (`dataUpdatedAt`) to the cutoff, not the clock now: a read taken a minute before the vote window closed is withheld and must not be called final afterwards.
- **A caller can choose.** `useMyAgenda` takes `freshness` (default `feed`; the 30-day look-back windows pass `slow`).
- **Audited reads are `static`.** The back-office audited lists and person records write an `ADMIN_PII_LISTED`/`ADMIN_PII_VIEWED` row per fetch, so a refetch on focus or on going back would pad the audit log with rows nobody asked for.
- **A longer tier exposes every missing invalidation**, because a stale entry no longer hides behind a refetch on mount. Giving a hook a tier means walking its writers.

### Query keys

- **Built by the builders** in `app/src/clubs/queryKeys.ts` (or the domain's own `queryKeys.ts`), never written inline in a hook. The inline literals that existed (RSVP history, the guest link, the WhatsApp settings and share) drifted from the key their invalidation spelled out.
- **Hierarchy: club, team, event, sub-query**, with the persona (`{ pour: playerId }`) as the **last** segment and absent for the user themself. A prefix invalidation therefore matches both personas, and switching persona never serves the other persona's cache. The sub-queries an event owns (`EventPart`: rsvps, convocations, jersey-duty, votes, scoresheet, scoresheet-extraction, whatsapp-share, rsvp-history) are built by `eventSubKey`, so one family across personas is one prefix.
- **A `{}` params segment means "lists only".** `teamEventsQueryKey(c, t)` ends in `{}` or the params object, so invalidating it never matches an event detail. Detail keys have a string where the lists have an object.
- **Root keys are prefixes of everything below.** `['clubs']`, `clubQueryKey(clubId)` and `teamQueryKey(clubId, teamId)` match every query of the club or team (rosters, events, stats, members). Invalidating one refetches every active query under it, which is what a bare `invalidateQueries(clubQueryKey(id))` used to do to patch one field. Use `exact: true`, or write the field with `setQueryData`.
- **Predicates for a shape a key cannot express.** `isEventDetailQuery` (the event itself, any persona, none of its sub-queries: `teamEventQueryKey` is a prefix of those too), `isTeamFamilyQuery(families, scope)` (a family of a team under whichever club read it, since a CTC team is reachable through each linked club), `isTeamAdminCandidatesQuery`, `isClubMeetingDependentQuery`. They match on the positions the builders lay out, so changing a builder means changing its predicate (`testCache.ts` seeds one entry per shape, so a drift shows up as a mutation test failing).
- **No `new Date()` in a key without rounding.** A bound stamped to the millisecond is a new entry per mount, never a hit, and entries pile up. `roundedNow()` (`app/src/clubs/myAgendaWindow.ts`) floors to 5 minutes; `playerAgendaWindowParams` and `pastMatchesWindowParams` default to it, and `useHomeAgendaParams` is the one place the home's window is chosen, so the dashboard and the bottom nav's badge read one entry. The `useMemo` around a window stays: a mounted screen should not slide to the next slot's key mid-visit.
- **One key per polled resource.** A count that only needs the unread number reads the bell's entry (`BELL_PARAMS`), not a `{ limit: 1 }` key of its own, which would be a second poller.

### Gating

- **`enabled` mirrors the server guard.** A query the viewer cannot read is never sent: it could only fail, and a failing query is retried on remount and focus. `GET .../admins` is allowed to club `ADMIN` and `MEMBER`, so `useIsTeamManager` gates on membership (and skips a club `ADMIN`, who is a manager without it); a guardian-only parent holds no membership and fires nothing. `GET /clubs/:id/players` is `ADMIN`-only, so only a club admin reads it. Read the controller's guard, not the screen, to decide the gate.
- **A page with tabs or dialogs loads what the hero, the tab list and the permission checks need, and the rest when the tab opens** (`enabled: activeTab === '…'`, or the dialog's `open`). `TeamDetailPage` is the reference: the roster table page, the partner-club page, the « À traiter » read and the add-player and add-admin pickers wait; the roster total, the owner club, the first events page and the admin list stay on every tab because the hero, the count badges and `useIsTeamManager` read them. Before gating a query, search for every reader of it, `total` included: gating the admin list or the full roster would have blanked a badge until the tab was visited.
- **A gated consumer keeps its own `error → loading → empty → data` branches.** A disabled query on its own active tab reports loading on the first render, so a gated tab does not flash its empty state; and a picker that loads on open shows `QueryError`, then a skeleton, then the form, never an empty select that reads as "no one to add".
- **Personas refresh on entry, not on every hook.** `useRefreshPersonasOnEntry` (an observer with `refetchOnMount: 'always'`) is mounted by `TeamDetailPage` and `EventDetailPage`; `useTeamPersona` only reads the list. `ActingAsProvider` keeps its own observer, so the list is always held.

### Mutations

- **Write the response into the cache, then invalidate only what the write changed elsewhere.** `setQueryData` for a plain record, `storeTeamEvent` for a `TeamEvent`. `storeTeamEvent` updates only an entry that already exists (a half-built entry would look fresh) and keeps the manager-only WhatsApp fields of the entry it replaces, because the own-answer routes (RSVP, clear, travel mode) assemble the event without them.
- **Never invalidate a key and then a key it already covers.** TanStack v5 invalidates with `cancelRefetch: true`: the second call cancels the fetch the first started and sends it again, so the request goes out twice. Before the overhaul an RSVP fetched the RSVP roster twice for this reason.
- **Never invalidate a prefix that covers the entry just written.** It refetches what the response already said. The event key is the prefix of all its sub-queries, so invalidating it after an RSVP also refetched the convocations, votes, scoresheet and share, none of which an RSVP can change.
- **Rare series-wide manager writes may use the team's `events` prefix; frequent per-player writes may not.** Event create, edit, time change, delete, FFBB import and a roster change are a manager's few-times-a-season actions, and a kick-off, a venue or a deletion really does reach the RSVP roster, the duty and the share message (`invalidateTeamEvents`, `invalidateRosterDependents`). An RSVP, a travel mode and a wash-duty write are fired by every player on every event, so their fan-out is listed entry by entry (`applyRsvpWrite`). A paginated list keeps a plain `invalidateQueries({ queryKey: <list>QueryKey })` for any mutation of it: the new row's position across every cached `(page, search, sortBy, …)` is not derivable from the response, and the cached variants may coexist.
- **A deliberate non-refetch is `refetchType: 'none'`.** The scoresheet extraction query is disabled while the OCR job runs; an upload or retry marks it stale without fetching, so a long tier cannot serve the old `FAILED` read as fresh when the job ends.
- **Do not patch what a response does not prove.** `useConfirmEmail` keeps its session invalidation instead of writing `emailVerified: true`: the confirm route is anonymous and answers 204 with no body, and its page sits outside `PublicOnlyRoute`, so the cached session may belong to another account or to nobody.

**What reads what.** A write must refresh the readers of the data it moves, not only the screen it came from. Walk this table for the data your mutation touches, and add a row when a new reader appears.

| Data                        | Reads                                                                                                                                      | Refreshed by                                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard (`MyAgendaEvent`) | logistics, the RSVP summary, `myConvocation`, `result`, the vote state, `meetingPlan`; « Joueurs au total » and the « sans compte » action | RSVP, convocation, logistics, meeting, vote, scoresheet confirm, event writes, team delete, roster and player writes (`invalidateDashboard`) |
| Wash duty and rotation      | RSVPs and convocations (`jersey-duty.service` builds its pool from both)                                                                   | RSVP set/clear, convocations, event writes, roster writes, an exemption (`invalidateJerseyRotation`)                                         |
| Event detail and lists      | the roster summary (`rosterSize`, counts), the answer, `logistics`, `result`, `meetingPlan`                                                | the event's own writes; any other persona's copy is marked stale by `invalidateOtherPersonas`/`invalidateEventDetails`                       |
| Team season stats           | played matches, every teammate's vote (awards)                                                                                             | event update and delete, vote cast, roster writes                                                                                            |
| `myTeams`                   | team name, category and gender, the roster, `isTeamAdmin`                                                                                  | team create/update (only when one of those three is sent)/delete, roster writes, team admin add/remove                                       |
| Personas                    | rosters (which team a child is on)                                                                                                         | roster writes (`invalidateRosterDependents`), and once per team or event page entry                                                          |
| Admin candidates            | every member of every club the team is linked to (not the admins: the page subtracts them client-side)                                     | club member add/remove, partner club add/remove. A player accepting an invite adds a member with no manager's write, hence `slow`            |
| Poule results               | the team's FFBB links, the calendar import                                                                                                 | FFBB link add/remove, import                                                                                                                 |
| Club (`ffbbClubCode`)       | nothing else under `['clubs', id]` reads it                                                                                                | `setQueryData` on the club entry from the response, never a prefix invalidation                                                              |

### Polling

The notification feed polls at 60 s (`POLL_INTERVAL_MS = FRESHNESS.feed`), and its `staleTime` equals the interval so a mount or a focus inside it does not race the poller. One key per polled resource; a reader of a part of it (the unread count) shares the entry. No SSE or websocket (see « Realtime » above): the payload is a handful of rows and the audience has one tab open.

### User switch

`replaceSession(queryClient, user | null)` (`app/src/auth/session.ts`) is the only way the logged-in user changes: login, register, logout, session expiry, and accepting a player or guardian invite (which logs the visitor in as the new account). It sets the session first and removes (not invalidates) every query whose key does not start with `auth`. With a user, the removal is immediate, since the protected tree is not mounted on the login and invite pages. With `null`, `useDropUserQueriesOnSessionEnd` (mounted by `AccountProvider`) removes them in an effect once `ProtectedRoute` has unmounted the tree, because removing the entries of still-mounted queries lets their next re-render rebuild them and fetch as nobody. Only a user-to-null transition counts, so a first visit that resolves to no session does not refetch a public page's data. Impersonation keeps `queryClient.clear()`. Rationale and the privacy angle: [`decisions/accounts-and-access.md`](./decisions/accounts-and-access.md).

### Cancellation

Every `queryFn` is `({ signal }) => apiClient.get(path, params, { signal })`; `post`, `put`, `patch` and `delete` are never cancelled by a component leaving. TanStack aborts a fetch whose last observer left or that a newer fetch superseded (a debounced search typed past, a tab left mid-load), so the browser drops the request instead of downloading an answer nobody reads. In `ApiClient` an abort rejects with the signal's `AbortError`, never an `ApiError`, and is checked before any status: it never refreshes the token, never fires the session-expiry or impersonation-expiry listeners. The refresh is single-use and shared (`sharedRefresh`), so a request that got a 401 waits for it through `waitForRefresh(signal)`, which stops waiting when the caller aborts and leaves the refresh running for the others; an aborted caller is not retried and does not report an expiry on its behalf. `fetchSession` forwards the signal to `/auth/me` and its back-off sleep and rethrows an abort instead of reading it as « no session ».

### Testing and measuring

- **Assert what a mutation refreshes and what it leaves alone.** `createSeededCache` seeds one entry per kind of query a team's writes can touch; the test runs the write and compares `staleLabels()` and `removedLabels()` with the exact expected set, so the convocations after an RSVP are pinned as untouched, not only the roster as refreshed.
- **Tiers and gating are tests too**: `freshnessTiers.test.tsx` (remount and focus read the cache for `static`/`slow`, the tier a hook really runs with, the data-dependent tiers as pure functions), `TeamDetailPage.test.tsx` (records every GET through MSW and asserts which tab or dialog fires which).
- **Count requests in a real browser when a change is about what is requested.** `pnpm mock-api --fixtures scripts/fixtures/request-count-{player,guardian,team-manager}.json` serves a player, a guardian-only parent and a club admin with the data the dashboard, team and event pages read; run the Vite dev server against it and drive Playwright (Chromium is preinstalled). Navigate **client-side** (`history.pushState` then a `popstate` event) so the cache lives across steps, count every `/api/*` response with `page.on('response')`, failures included, and report per step: `/dashboard` cold load, team page, event page, back, back. For freshness, wait past the tier (33 s clears `live`) and fire a `visibilitychange` blur and focus. Measure the same path on the code before the change, at 390 and 1280 wide (the bottom nav fetches only on a phone). The fixture dates are absolute (the match is on 2026-10-09): after that the dashboard window no longer holds it and the numbers change, so refresh the dates before comparing. The counting script is not committed; the recipe above is its whole content.
